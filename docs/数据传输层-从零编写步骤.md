# 数据传输层 —— 从零编写步骤

> 目标：手写一条「ESP32 → UART → STM32」的可靠二进制数据传输层。
> 全文分 9 个里程碑，**每个里程碑都有"通过标准"，没通过不要往下走**。

---

## 总原则（三条，违反任何一条都会让你怀疑人生）

1. **先单端，后双端** —— 一端的组帧/解析先在 PC 上验证，再上硬件。
2. **先无 ACK，后有 ACK** —— ACK 引入双向时序，失败时分不清是"没收对"还是"ACK 没回来"。
3. **CRC 先对通，再谈收发** —— CRC 是整条链路的裁判，裁判不准，后面全是白干。

---

## 里程碑 0｜把协议写在纸上（不写代码）

这一步产出**一张表**。所有数字一旦定下来，后面任何一处改动都要两端同步。

### 帧格式

| 偏移 | 宽度 | 字段 | 值 / 含义 |
|---|---|---|---|
| 0 | 1 B | 帧头 | `0xAA` |
| 1 | 1 B | 帧头 | `0x55` |
| 2 | 2 B | 长度 `flen` | 小端，`= 3 + payload_len` |
| 4 | 1 B | 命令 `cmd` | 见命令表 |
| 5 | 2 B | 序号 `seq` | 小端 |
| 7 | N B | 载荷 | `N = flen - 3` |
| 7+N | 4 B | CRC32 | 小端，覆盖 `[cmd, seq, payload]` |
| 11+N | 2 B | 帧尾 | `0x0D 0x0A` |

**总长 = 13 + N**

### 现在就必须定死的 5 个决策

| 决策项 | 定值 | 定了之后改的代价 |
|---|---|---|
| 字节序 | **小端** | 两端都要改 |
| 长度字段含义 | **`3 + payload_len`**（只描述 CRC 覆盖范围） | 两端都要改 |
| CRC 覆盖范围 | **`cmd + seq + payload`** | 两端都要改 |
| CRC 参数 | poly `0xEDB88320`、反射、初值 `0xFFFFFFFF`、输出异或 | 两端都要改 |
| 分片大小 | **256 B**（受接收侧 DMA 半缓冲约束） | 两端都要改，且包数全变 |

### 通过标准

**能手算出一帧 `CMD_START(size=5604, pkts=22)` 的完整 19 字节。**

对照答案：

```
payload  = E4 15 00 00 | 16 00        (5604=0x15E4, 22=0x0016, 小端)
flen     = 3 + 6 = 9                  → 09 00
整帧     = AA 55 09 00 01 00 00 E4 15 00 00 16 00 <CRC 4B> 0D 0A
总长     = 13 + 6 = 19 字节
```

> 算不出来就说明「长度字段」和「CRC 覆盖范围」的关系还没理顺，先别写代码。

## 里程碑 1｜整数 ↔ 字节：四个小函数

**为什么先写这个**：后面 `send_frame`、`parse_frame`、ACK、START、END 全都在用它。现在封装好，后面每处只写一行。

```c
/* ---------- 拆：整数 → 字节数组（写成小端） ---------- */
static inline void put_u16(uint8_t *p, uint16_t v)
{
    p[0] = (uint8_t)(v & 0xFF);          /* 低字节在前 */
    p[1] = (uint8_t)(v >> 8);
}

static inline void put_u32(uint8_t *p, uint32_t v)
{
    p[0] = (uint8_t)(v & 0xFF);
    p[1] = (uint8_t)((v >> 8)  & 0xFF);
    p[2] = (uint8_t)((v >> 16) & 0xFF);
    p[3] = (uint8_t)((v >> 24) & 0xFF);
}

/* ---------- 拼：字节数组 → 整数 ---------- */
static inline uint16_t get_u16(const uint8_t *p)
{
    return (uint16_t)((uint16_t)p[0] | ((uint16_t)p[1] << 8));
}

static inline uint32_t get_u32(const uint8_t *p)
{
    return (uint32_t)p[0]
         | ((uint32_t)p[1] << 8)
         | ((uint32_t)p[2] << 16)
         | ((uint32_t)p[3] << 24);
}
```

### 三个必须注意的细节

1. **`put_*` 里每个赋值都要 `(uint8_t)` 强转** —— 显式截断，避免编译器警告，也表明意图。
2. **`get_*` 里强转必须在移位之前** —— `p[3] << 24` 时 `p[3]` 会被提升为 `int`，若值是 `0x80` 会溢出符号位，属未定义行为。
3. **`static inline`** —— 放头文件里，两边工程都能用，不占调用开销。

### 通过标准

`get_u16(put_u16 的输出)` 必须等于原值。取 1000 个随机数跑一遍，0 个失败。

### 建议做法

在 PC 上用 Python 或 20 行 C 验证，**不要烧到板子上试**：

```python
def put_u16(v):  return bytes([v & 0xFF, (v >> 8) & 0xFF])
def get_u16(b):  return b[0] | (b[1] << 8)

import random
for _ in range(1000):
    v = random.randint(0, 0xFFFF)
    assert get_u16(put_u16(v)) == v
print("u16 ok")
```

## 里程碑 2｜CRC32：写两个版本互相印证

### 版本 A：按位实现（慢，但逻辑一眼可读，用作基准）

```c
uint32_t crc32_bitwise(const uint8_t *d, uint32_t len)
{
    uint32_t crc = 0xFFFFFFFFUL;
    for (uint32_t i = 0; i < len; i++) {
        crc ^= d[i];
        for (int k = 0; k < 8; k++) {
            crc = (crc >> 1) ^ (0xEDB88320UL & (uint32_t)(-(int32_t)(crc & 1)));
        }
    }
    return ~crc;
}
```

### 版本 B：查表实现（快，最终使用）

```c
static const uint32_t s_crc_table[256] = { /* 表内容见项目 ota_protocol.c */ };

/* 流式：把上一次的结果传进来接着算，第一次传 0 */
uint32_t ota_crc32_update(uint32_t crc, const uint8_t *data, uint32_t len)
{
    crc = ~crc;                                        /* 进入取反 */
    while (len--) {
        crc = (crc >> 8) ^ s_crc_table[(crc ^ *data++) & 0xFFUL];
    }
    return ~crc;                                       /* 返回再取反 */
}
```

### 通过标准（三条必须全过）

| # | 验证内容 | 期望 |
|---|---|---|
| 1 | 对字符串 `"123456789"` 算 CRC32 | `0xCBF43926`（标准测试向量） |
| 2 | 版本 A 与版本 B 对同一段随机数据 | 结果完全相同 |
| 3 | **流式验证**：把 269 字节切成 3 段分别累计 | 等于一次算完 |

**第 3 条是关键**——它就是「ESP32 边发边算」和「STM32 边收边算」最终能对上的数学依据。

```python
# 用 Python 的 zlib 交叉验证你的 C 实现
import zlib, random
data = bytes(random.getrandbits(8) for _ in range(269))
print(hex(zlib.crc32(data) & 0xFFFFFFFF))
# 把同样的数据喂给 STM32，结果必须一样
```

> 如果 Python 的 `zlib.crc32` 和你的结果不一样 → 多项式或初值错了，**立刻停下来修**，不要带着错的 CRC 往下走。

## 里程碑 3｜组帧函数（只写，不接硬件）

```c
/**
 * @brief 把 cmd / seq / payload 组一帧
 * @param out      输出缓冲
 * @param out_cap  缓冲容量
 * @return 整帧字节数；0 表示缓冲不够
 */
uint16_t frame_build(uint8_t cmd, uint16_t seq,
                     const uint8_t *payload, uint16_t plen,
                     uint8_t *out, uint16_t out_cap)
{
    uint16_t flen  = (uint16_t)(3 + plen);
    uint16_t total = (uint16_t)(13 + plen);

    if (total > out_cap) {
        return 0;                       /* 容量检查，永远不要省 */
    }

    out[0] = 0xAA;
    out[1] = 0x55;
    put_u16(&out[2], flen);
    out[4] = cmd;
    put_u16(&out[5], seq);
    if (plen > 0 && payload != NULL) {
        memcpy(&out[7], payload, plen);
    }
    put_u32(&out[7 + plen], ota_crc32_update(0, &out[4], flen));
    out[11 + plen] = 0x0D;
    out[12 + plen] = 0x0A;
    return total;
}
```

### 设计要点

- **返回 `total` 而不是 `void`** —— 调用方要用它决定"发多少字节"。
- **`&out[4]` + `flen` 的巧合** —— CRC 从 `cmd` 开始算 `flen` 个字节，恰好覆盖 `cmd + seq + payload` 三部分，一字节不多不少。这正是长度字段定义成 `3 + plen` 的好处。
- **`payload` 可以为 NULL** —— `CMD_GET_INFO` / `CMD_END` 用空载荷。
- **容量检查放在最前面** —— 越界是嵌入式里最难查的 bug，养成习惯。

### 通过标准

用 `CMD_START, seq=0, payload={E4 15 00 00 16 00}` 调用，打印出的 19 字节，**逐字节等于里程碑 0 手算的结果**（CRC 字段除外，那个用 Python 算）。

### 建议做法

写一个 PC 小程序，把十六进制打印出来，和手算结果并排看：

```c
/* 在 PC 上（Windows/VS 或 gcc）单独跑这个函数，不碰 MCU */
int main(void) {
    uint8_t pl[6] = {0xE4,0x15,0x00,0x00,0x16,0x00};
    uint8_t out[64];
    uint16_t n = frame_build(0x01, 0, pl, 6, out, sizeof(out));
    printf("total=%u\n", n);
    for (uint16_t i = 0; i < n; i++) printf("%02X ", out[i]);
    return 0;
}
```

## 里程碑 4｜解析函数 + PC 回环测试

```c
/**
 * @brief 从缓冲区解析一帧
 * @return 0 成功; -1 无帧头/长度不足; -2 CRC 错; -3 帧尾错
 */
int frame_parse(const uint8_t *buf, uint32_t len, OtaFrame_t *fr)
{
    uint32_t i = 0;

    if (buf == NULL || fr == NULL || len < 13) {
        return -1;
    }

    /* 1. 滑动搜索帧头（容忍前面的脏字节） */
    while (i + 13 <= len) {
        if (buf[i] == 0xAA && buf[i + 1] == 0x55) break;
        i++;
    }
    if (i + 13 > len) return -1;

    /* 2. 长度字段 */
    const uint8_t *p = &buf[i];
    uint16_t flen = get_u16(&p[2]);
    if (flen < 3) return -1;

    /* 3. 整帧是否完整 */
    uint32_t total = 10u + flen;              /* 帧头2+长度2 + CRC4 + 帧尾2 = 10 */
    if (i + total > len) return -1;

    /* 4. CRC 校验 */
    if (ota_crc32_update(0, &p[4], flen) != get_u32(&p[4 + flen])) return -2;

    /* 5. 帧尾校验 */
    if (p[8 + flen] != 0x0D || p[9 + flen] != 0x0A) return -3;

    /* 6. 填充结果（零拷贝：payload 直接指向 buf 内部） */
    fr->cmd         = p[4];
    fr->seq         = get_u16(&p[5]);
    fr->payload     = &p[7];
    fr->payload_len = (uint16_t)(flen - 3);
    return 0;
}
```

### 三个设计要点

1. **`total = 10 + flen`** —— 别硬编码成 `13 + N`，那是"已知 N"的算法；解析时 N 是未知的，只能用 `flen` 推。二者等价：`10 + (3 + N) = 13 + N`。
2. **6 个 return 分支各对应一种损坏** —— 这是排查时的路标，不要图省事都返回 -1。
3. **`payload` 是指针，零拷贝** —— 代价是它只在 `buf` 有效期内有效。调用方**必须**保证解析后立刻处理，或先 `memcpy` 出来。

### PC 回环测试（最重要的一步）

在 PC 上把 `frame_build` 的输出直接喂给 `frame_parse`，跑一万次随机数据：

```python
# tools/frame_roundtrip.py
import random, zlib

def build(cmd, seq, payload):
    flen = 3 + len(payload)
    body = bytes([cmd]) + seq.to_bytes(2, 'little') + payload
    crc  = zlib.crc32(body) & 0xFFFFFFFF
    return (b'\xAA\x55' + flen.to_bytes(2, 'little') + body
            + crc.to_bytes(4, 'little') + b'\x0D\x0A')

def parse(buf):
    i = 0
    while i + 13 <= len(buf) and buf[i:i+2] != b'\xAA\x55':
        i += 1
    if i + 13 > len(buf): return None
    p = buf[i:]
    flen = int.from_bytes(p[2:4], 'little')
    total = 10 + flen
    if len(p) < total: return None
    if zlib.crc32(p[4:4+flen]) & 0xFFFFFFFF != int.from_bytes(p[4+flen:8+flen], 'little'):
        return None
    if p[8+flen:10+flen] != b'\x0D\x0A': return None
    return (p[4], int.from_bytes(p[5:7], 'little'), p[7:7+flen-3])

for _ in range(10000):
    n  = random.randint(0, 256)
    pl = bytes(random.getrandbits(8) for _ in range(n))
    f  = build(0x02, random.randint(0, 65535), pl)
    assert len(f) == 13 + n
    r  = parse(b'\x00\xFF\x13' + f + b'\x99')   # 故意加脏字节，测滑动搜索
    assert r is not None and r[2] == pl
print("roundtrip ok")
```

### 通过标准

- 一万次随机 payload 全部通过
- **故意在帧前面塞 3 个脏字节**，仍能正确解析（验证滑动搜索）
- **故意改坏 CRC 的一个 bit**，解析必须返回失败

## 里程碑 5｜STM32 接收通路（★ 分两小步，别一步到位）

### 5a 先用阻塞轮询（排除 DMA 这个变量）

```c
uint8_t buf[512];
if (HAL_UART_Receive(&huart2, buf, 269, 3000) == HAL_OK) {
    OtaFrame_t f;
    int rc = frame_parse(buf, 269, &f);
    /* 打印 rc 和 f.seq */
}
```

**通过标准**：用串口助手手工发一帧，STM32 能解析出正确的 `cmd` / `seq`。

**为什么先做这一步**：
- 如果 polling 都收不对 → 问题在**协议**（长度字段、CRC 覆盖范围）
- 如果 polling 对、DMA 不对 → 问题在 **DMA 配置**
- 这个二分法能帮你砍掉一半的排查范围

### 5b 再换 DMA + IDLE

```c
#define RX_BUF_SIZE   2048
uint8_t           RxBuf[RX_BUF_SIZE];
volatile uint8_t  RxReady = 0;
volatile uint16_t RxLen   = 0;

void RxStart(void)
{
    HAL_UART_DMAStop(&huart2);                    /* 1 停掉可能残留的 DMA */
    RxReady = 0;
    RxLen   = 0;
    __HAL_UART_CLEAR_IDLEFLAG(&huart2);           /* 2 清 IDLE 标志 */

    HAL_UART_Receive_DMA(&huart2, RxBuf, RX_BUF_SIZE);   /* 3 启动 */

    /* 4 ★ 启动之后再关 HT/TC —— 顺序反了等于没关，
     *    因为 HAL 在启动时会重新打开它们 */
    DMA1_Channel6->CCR &= ~(DMA_CCR_HTIE | DMA_CCR_TCIE);
    DMA1->IFCR = DMA_IFCR_CGIF6;                  /* 5 清 DMA 通道标志 */

    __HAL_UART_ENABLE_IT(&huart2, UART_IT_IDLE);  /* 6 只留 IDLE */
}
```

中断服务函数：

```c
void USART2_IRQHandler(void)
{
    if (__HAL_UART_GET_FLAG(&huart2, UART_FLAG_IDLE) != RESET) {
        __HAL_UART_CLEAR_IDLEFLAG(&huart2);

        if (!RxReady) {
            uint16_t remain = (uint16_t)__HAL_DMA_GET_COUNTER(huart2.hdmarx);
            uint16_t len    = (uint16_t)(RX_BUF_SIZE - remain);
            if (len > 0 && len <= RX_BUF_SIZE) {
                RxLen   = len;
                RxReady = 1;
            }
        }
        HAL_UART_DMAStop(&huart2);
        return;                     /* ★★ 直接返回，不要调 HAL_UART_IRQHandler */
    }
    HAL_UART_IRQHandler(&huart2);   /* 其它事件（ORE/FE/NE/PE）才交给 HAL */
}
```

主循环：

```c
while (1) {
    if (RxReady) {
        uint16_t len = RxLen;
        memcpy(FrameBuf, RxBuf, len);          /* 1 快照 */
        memset(RxBuf, 0, RX_BUF_SIZE);         /* 2 清缓冲 */
        RxReady = 0;
        RxStart();                             /* 3 ★ 立刻重启，准备收下一帧 */

        OtaFrame_t f;
        if (frame_parse(FrameBuf, len, &f) == 0) {
            HandleFrame(&f);                   /* 4 最后才慢慢处理 */
        }
    }
}
```

### 通过标准

连发 100 帧，**每一帧**都进中断且 `RxLen` 正确（在中断里翻转 LED 计数）。

### 三个必须理解的因果（这也是面试高频题）

| 做法 | 不这么做会怎样 |
|---|---|
| 关 `HTIE\|TCIE` | 缓冲区收到一半（1024B）就触发"接收完成"回调，产生**假帧** |
| **启动之后**才关 | HAL 在 `HAL_UART_Receive_DMA` 里会重新打开它们，先关就白关了 |
| 处理完 IDLE 直接 `return` | `HAL_UART_IRQHandler` 处理一次 IDLE 后会 `ATOMIC_CLEAR_BIT(CR1, IDLEIE)`，**永久关掉空闲中断**，后面再也收不到 |

## 里程碑 6｜单向传送（先不要 ACK）

- **ESP32**：连发 22 包，发完就下一包，不等任何回复
- **STM32**：每收一帧，把 `received` 累加并打印

### 通过标准

STM32 收到的总字节数 = 5604，且**顺序连续不断**。

### 为什么跳过 ACK

ACK 引入了**双向时序**：一旦失败，你分不清是「STM32 没收对」还是「ACK 没能传回来」还是「ESP32 等 ACK 时把下一帧吃掉了」。先把这三件事拆开。

单向都传不过去 → 问题在链路或 DMA。
单向能过、双向不行 → 问题一定在**时序**（等 ACK 的逻辑、缓冲区复用）。

## 里程碑 7｜加 ACK + 重传

### STM32 侧：组一个 3 字节载荷的 ACK

```c
void SendAck(uint16_t seq, uint8_t status)
{
    uint8_t pl[3];
    put_u16(pl, seq);
    pl[2] = status;

    uint8_t out[64];                     /* ACK 帧只有 16 字节，64 足够 */
    uint16_t n = frame_build(0x03, 0, pl, 3, out, sizeof(out));
    HAL_UART_Transmit(&huart2, out, n, 100);   /* 阻塞发送，100ms 超时 */
}
```

### ESP32 侧：发送 + 等 ACK + 重传

```c
int send_and_wait_ack(uint8_t cmd, uint16_t seq,
                      const uint8_t *pl, uint16_t plen)
{
    for (int r = 0; r < MAX_RETRY; r++) {
        send_frame(cmd, seq, pl, plen);
        uart_wait_tx_done(UART_PORT, pdMS_TO_TICKS(1000));   /* ★ 必须等发完 */

        parsed_frame_t fr;
        if (read_frame(&fr, ACK_TIMEOUT_MS) && fr.cmd == 0x03) {
            if (get_u16(fr.payload) == seq) {
                return fr.payload[2];         /* 返回 status */
            }
            /* ACK 序号不匹配（旧 ACK 迟到）→ 重发 */
        }
        ESP_LOGW(TAG, "[RETRY] seq=%u try %d/%d", seq, r + 1, MAX_RETRY);
    }
    return -1;
}
```

### 通过标准

1. 正常升级能跑完，Monitor 里看到 `Progress` 一路到 100%
2. **人为打断**：升级中途把 STM32 复位一下 → ESP32 必须打印 5 次 `[RETRY]` 然后 `ABORT`
   - 这条才真正证明**重传逻辑在跑**，而不是"碰巧每次都成功"

### 三个容易翻车的点

| 点 | 说明 |
|---|---|
| `uart_wait_tx_done` 不能省 | `out` 是 `static`，不等发完就返回，下一帧会覆盖正在传输的数据 |
| ACK 要校验 `seq` | 否则上一包的迟到 ACK 会被当成这一包的，造成**错包静默通过** |
| 重复包要幂等 | STM32 收到 `seq == expect - 1` 时**只补 ACK，不重写 Flash** |

## 里程碑 8｜会话控制（START / END）

### CMD_START（ESP32 → STM32）

载荷 6 字节：`size(4B) + 总包数(2B)`

STM32 收到后：
1. 校验 `size` 是否超过分区容量、`pkts` 是否为 0
2. **擦除暂存区**
3. `active = 1`，清空会话状态
4. 回 ACK

**为什么把"擦除"放在 START**：擦除 240KB 要几百毫秒。放在这里，用户能感知的开销只有一次；放在每包前面会让每包耗时抖动。

### CMD_END（ESP32 → STM32）

载荷 4 字节：发送端累计的整镜像 CRC32

STM32 比对：
```c
if (received == fw_total && crc == crc_sent) { /* 通过 */ }
```

### 通过标准

**故意改坏固件一个字节**（CRC 就变了）→ STM32 必须回 `ACK_ERR`，ESP32 打印 `CRC mismatch`。

## 里程碑 9｜落 Flash + 校验 + 跳转

顺序（每一步都不能颠倒）：

```
1. flash_erase_region(APP_B_ADDR, APP_B_SIZE)      // START 时已做
2. flash_write_bytes(dst, payload, len)            // 每包写入
3. 回读校验（写多少读多少，逐字节比对）
4. flash_copy_appb_to_appa(fw_total)               // END 通过后
5. 回读 App A 再算一次整体 CRC
6. config_write(&cfg)                              // 写"升级成功"标记
7. NVIC_SystemReset()                              // 复位跳新固件
```

### 写入的粒度问题

STM32F1 的 Flash 编程粒度是**半字（16 位）或字（32 位）**，不能按字节写：

```c
for (uint32_t off = 0; off < len; off += 4) {
    uint8_t  tmp[4] = {0xFF, 0xFF, 0xFF, 0xFF};       /* 擦除态填充 */
    uint32_t chunk  = (len - off > 4) ? 4 : (len - off);
    for (uint32_t k = 0; k < chunk; k++) tmp[k] = src[off + k];
    uint32_t word = (uint32_t)tmp[0] | ((uint32_t)tmp[1] << 8)
                  | ((uint32_t)tmp[2] << 16) | ((uint32_t)tmp[3] << 24);
    HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, dst + off, word);
}
```

**为什么不能写 `*(uint32_t*)src`**：`src` 是载荷指针（比如 `&buf[7]`），地址不保证 4 字节对齐，Cortex-M3 上会 HardFault 或效率极差。

### 通过标准

升级完成后自动重启，LED 节奏从「200ms 慢闪（下载模式）」变成「150ms 快闪（App 运行）」。

## 附：整个过程的调试策略

见配套图 —— **三个联调阶段，每个阶段只引入一个新变量**：

| 阶段 | 连线 | 这一阶段引入的新变量 | 能定位的问题 |
|---|---|---|---|
| ① | PC 脚本 ↔ STM32 | STM32 的接收通路 | 帧收得对不对、DMA/IDLE 配置对不对 |
| ② | ESP32 ↔ PC 脚本 | ESP32 的组帧 | 字节序、长度字段、CRC 覆盖范围对不对 |
| ③ | ESP32 ↔ STM32 | 双向时序 | 只剩 ACK 等待、缓冲区复用这类时序问题 |

### 三条铁律

1. **每个里程碑都有自己的通过标准，别跳过** —— 跳过的代价是后面用两倍时间找回来。
2. **一次只引入一个新变量** —— 同时改三处还失败了，你等于什么都没学到。
3. **任何"时好时坏"的现象，先怀疑时序，再怀疑协议** —— 协议错了是稳定错，时序错了才是时好时坏。

## 附：优先级建议（时间不够时先做哪些）

| 优先级 | 里程碑 | 理由 |
|---|---|---|
| P0 | 0 → 1 → 2 | 不写代码就能做完，却是后面所有代码的地基 |
| P0 | 3 → 4 | 纯逻辑，PC 上就能跑通，风险最低 |
| P1 | 5a → 5b | 硬件相关，最容易出问题，所以要分两步 |
| P1 | 6 → 7 | 先单向后双向，把变量拆开 |
| P2 | 8 → 9 | 会话控制与落盘，逻辑直白，风险低 |

**如果只想要一个"能跑起来"的最小版本**：0 → 1 → 2 → 3 → 4 → 5b → 6 → 9。
跳过 ACK 和 START/END 也能升级成功，只是没有重传保护和完整性校验。

## 附：三个容易被忽略但很重要的习惯

1. **每处 `memcpy` 前都问一句"放得下吗"**
   看 `frame_build` 的 `out_cap` 参数、`read_frame` 的 `total > sizeof(buf)` 检查——都是这个习惯的产物。

2. **发送缓冲用 `static` + 阻塞等待发完**
   `static` 避免每帧 malloc；`uart_wait_tx_done` 避免下一帧覆盖正在发的内容。两者必须配套。

3. **`volatile` 只给"中断改、主循环读"的标志**
   大数组不加（浪费性能且没用），标志变量不加（编译器会优化掉你的判断）。
